## What is the TLS 1.2 handshake

The **TLS 1.2 handshake** is the process that a **client** (e.g., browser) and **server** go through to:

- Agree on protocol version and cipher suite
- Authenticate the server (and optionally the client)
- Establish shared **session keys** for symmetric encryption
- Ensure integrity of all handshake messages

Only after this handshake completes successfully does **encrypted application data** (e.g., HTTPS traffic) start flowing.

---

## Handshake stages

### 1. ClientHello

**Direction:** Client → Server  

The client starts the handshake by sending a **ClientHello** message. It includes:

- **Protocol version:** e.g., TLS 1.2
- **Client random:** a cryptographically secure random value
- **Supported cipher suites:** list of algorithms (e.g., TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256)
- **Supported compression methods:** usually “null” in modern TLS
- **Extensions:** e.g., SNI (Server Name Indication), supported elliptic curves, etc.

**Purpose:**

- Tells the server: “Here is what I support; let’s agree on how to talk securely.”
- Provides the **client_random**, which will later be used in key derivation.

---

### 2. ServerHello

**Direction:** Server → Client  

The server responds with a **ServerHello** message. It includes:

- **Protocol version:** chosen version (e.g., TLS 1.2)
- **Server random:** another random value generated by the server
- **Selected cipher suite:** one from the client’s list
- **Selected compression method**
- **Extensions:** matching or responding to client extensions

**Purpose:**

- Confirms the protocol version and cipher suite to be used.
- Provides the **server_random**, also used later in key derivation.

---

### 3. Certificate exchange

**Direction:** Server → Client  

The server sends its **certificate chain** in a **Certificate** message:

- **Server certificate:** contains the server’s public key and identity (CN, SAN, etc.)
- **Intermediate CA certificates:** if needed
- **Root CA:** usually already trusted by the client and not always sent

Optionally, depending on the cipher suite, the server may also send:

- **ServerKeyExchange:** for ephemeral key exchange methods (e.g., ECDHE)
- **CertificateRequest:** if the server wants to authenticate the client (mutual TLS)

The client then performs **certificate validation**:

- Checks the certificate is **not expired**
- Verifies the **signature chain** up to a trusted CA
- Confirms the **hostname** matches the certificate (e.g., `example.com`)
- Ensures it is not revoked (via CRL/OCSP, depending on implementation)

If validation fails, the client will show a **security warning** or abort the handshake.

---

### 4. Key exchange

The **key exchange** step depends on the chosen cipher suite. Two common patterns in TLS 1.2:

1. **RSA key exchange (older, less preferred)**
2. **Ephemeral Diffie–Hellman (DHE/ECDHE) key exchange (preferred)**

#### 4.1 RSA key exchange (simplified)

- The server’s certificate contains an **RSA public key**.
- The client generates a random **pre‑master secret**.
- The client encrypts the pre‑master secret with the server’s **RSA public key**.
- The client sends this encrypted pre‑master secret in a **ClientKeyExchange** message.
- The server decrypts it using its **RSA private key**.

Both sides now share the same **pre‑master secret**.

#### 4.2 ECDHE (ephemeral Diffie–Hellman) key exchange (simplified)

- The server sends its **ephemeral public key** (e.g., ECDHE parameters) in **ServerKeyExchange**.
- The client generates its own **ephemeral key pair** and sends its **ephemeral public key** in **ClientKeyExchange**.
- Both client and server compute a shared **pre‑master secret** using the Diffie–Hellman algorithm:
  - Client: `pre_master_secret = f(client_private, server_public)`
  - Server: `pre_master_secret = f(server_private, client_public)`
- Due to the properties of Diffie–Hellman, both compute the same value.

This provides **forward secrecy**: even if the server’s long‑term private key is later compromised, past session keys remain safe.

---

### 5. Session key generation

Once both sides share the **pre‑master secret**, they derive the **master secret** and then the **session keys**.

In TLS 1.2, this uses a **PRF (Pseudo‑Random Function)** based on HMAC and a hash function (e.g., SHA‑256).

- Inputs:
  - `pre_master_secret`
  - `client_random`
  - `server_random`

From these, they derive:

- **Master secret**
- **Symmetric encryption keys** (client_write_key, server_write_key)
- **MAC keys** (client_write_MAC_key, server_write_MAC_key) for integrity
- **Initialization vectors (IVs)** if needed by the cipher mode

Both client and server perform the same calculations and end up with identical key material.

---

### 6. Finished messages

After key generation, both sides switch to **encrypted** messages.

#### 6.1 ChangeCipherSpec

- **Client → Server:** `ChangeCipherSpec`
  - Tells the server: “From now on, I will use the newly negotiated keys and algorithms.”
- **Server → Client:** `ChangeCipherSpec`
  - Same meaning in the opposite direction.

#### 6.2 Finished

- **Client → Server:** `Finished` (encrypted and MAC‑protected)
  - Contains a hash of all previous handshake messages.
- **Server → Client:** `Finished` (encrypted and MAC‑protected)
  - Also contains a hash of all previous handshake messages.

**Purpose:**

- Confirms that both sides:
  - Derived the same keys
  - Saw the same handshake transcript
  - Are now ready for secure application data

If the hashes do not match, the handshake fails.

  |                                                 |

  |                                                 |
  | <----------- ChangeCipherSpec ----------------- |
  | <----------- Finished (encrypted) ------------- |
  |                                                 |
  |        [Secure, encrypted application data]     |
  | <=============================================> |

## How encryption keys are agreed securely

This section explains, step by step, how the client and server end up with the **same encryption keys** without ever sending those keys directly over the network.

---

### Step 1 – Random values

Both sides contribute randomness:

- **ClientHello:** includes `client_random`
- **ServerHello:** includes `server_random`

These values are:

- Publicly visible (not secret)
- Used later in key derivation
- Ensure every TLS session produces unique keys, even if the same pre-master secret were somehow reused.

---

### Step 2 – Pre‑master secret

The **pre‑master secret** is the first shared secret that only the client and server know.

#### RSA key exchange (older method)

- Client generates a random pre‑master secret.
- Client encrypts it with the server’s **RSA public key** (from the certificate).
- Client sends the encrypted pre‑master secret in **ClientKeyExchange**.
- Server decrypts it using its **RSA private key**.

Both sides now share the same pre‑master secret.

#### ECDHE key exchange (preferred, provides forward secrecy)

- Server sends its **ephemeral public key** in `ServerKeyExchange`.
- Client generates its own ephemeral key pair and sends its **public key** in `ClientKeyExchange`.
- Both compute the same pre‑master secret using Diffie–Hellman math:
  - Client: `f(client_private, server_public)`
  - Server: `f(server_private, client_public)`

An attacker observing the public keys cannot compute the secret without the private key.

---

### Step 3 – Master secret

Using the **pre‑master secret**, `client_random`, and `server_random`, both sides compute the **master secret** using the TLS 1.2 PRF:

master_secret = PRF(pre_master_secret, "master secret",client_random + server_random)

- The label "master secret" is a constant string used in the PRF.
- `client random + server random` means concatenation.
- Both sides perform the same calculation and obtain the same `master secret`.

---

### Step 4 – Session keys

From the **master secret**, both sides derive the actual **session keys** used for encryption and integrity:

key_block = PRF(master_secret, "key expansion", server_random + client_random)

From this key block, they extract:

- `client_write_MAC_key`
- `server_write_MAC_key`
- `client_write_key`
- `server_write_key`
- IVs (if required)

Keys are **directional** to prevent reflection attacks.

---

### Step 5 – Integrity of the handshake

The **Finished** messages ensure that:

- Both sides derived the same keys
- No handshake messages were modified

Each Finished message contains:

- A hash of all previous handshake messages
- Encrypted and MAC‑protected with the newly derived keys

If anything was tampered with, the Finished verification fails.

---

## Summary

In TLS 1.2:

- **ClientHello** and **ServerHello** negotiate protocol version, cipher suite, and exchange random values.
- **Certificate** and optional **ServerKeyExchange** authenticate the server and provide key exchange parameters.
- **ClientKeyExchange** completes the key exchange, allowing both sides to compute a shared **pre‑master secret**.
- Using the pre‑master secret and random values, both sides derive a **master secret** and then **session keys**.
- **ChangeCipherSpec** and **Finished** messages switch the connection to encrypted mode and verify handshake integrity.

The result is a secure channel providing:

- **Confidentiality** (encryption)
- **Integrity** (MAC/AEAD)
- **Authentication** (certificates)

This is the foundation of secure communication in TLS 1.2 and HTTPS.
